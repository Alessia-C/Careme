# Backend architecture

Moved from CLAUDE.md. Read it when adding or changing an endpoint, middleware or session logic.

- **Backend** (`api/`): Vercel serverless functions (a standalone file `api/foo.ts` → `/api/foo`). Domains: `/api/auth` (done), `/api/users`, `/api/products` (`POST /api/products`, `GET /api/products`, `GET /api/products/:id`, `PUT /api/products/:id` and `DELETE /api/products/:id` done; the body validation shared by create and update is `api/products/_validation.ts`). Express is mandatory for the backend. Structure: one Express app per domain, exposed as a catch-all Vercel function (`api/auth/[...path].ts`, later `api/users/[...path].ts`; `api/products/` has both `[...path].ts` and `index.ts`, because a catch-all never matches `/api/products` itself), each with its own router and a feature-oriented layout. In `api/auth/` only `[...path].ts` is a function; everything else starts with `_` (`_app.ts` builds the app, `_router.ts` has the routes, `_routes/<endpoint>.ts` the handlers with their tests), because Vercel deploys every other file in `api/` as a function. Shared middleware lives in `api/_lib/`; `api/health.ts` stays a separate lightweight function (UptimeRobot) and does not load the Express apps. The reason is cost: keep the function count well under the Vercel Hobby cap. Migrate one domain at a time, keeping URLs, cookies and tests working. Use `/backend` (agent `backend-architect`) to design or review endpoints. Files/dirs prefixed with `_` (e.g. `api/_lib/`) are shared helpers, not routes. Inside an Express app do not wrap handlers with `withSentry()`: Express 5 forwards what a handler throws to `errorHandler` (`api/_lib/sentry.ts`, the last middleware of the app), which captures it and returns a generic 500, while body-parser errors become a 4xx without Sentry; `withSentry()` stays only for standalone functions such as `api/sentry-test.ts`. Compose handlers as `withMethod('POST', withObjectBody(handler))` using the helpers in `api/_lib/http.ts`, and register routes with `router.all(path, handler)` so `withMethod` keeps answering 405 (a path serving several methods uses `withMethods({ GET: list, POST: create })`; Express would give 404 or an automatic OPTIONS 200). Cookies are read with `getCookie(req, name)` from `api/_lib/cookies.ts` (no `cookie-parser`, no `req.cookies`). Route tests wrap the handler with `withErrorHandler` from `api/_lib/test-helpers.ts`; wiring (404, 405, body parser, ordering) is tested over real HTTP in `api/auth/_app.test.ts` (`// @vitest-environment node`). Protected endpoints add `withAuth(handler)` from `api/_lib/auth.ts`, the single point of JWT enforcement: it verifies the token with Supabase `getUser`, rejects `blocked` users and passes `{ id, email, role }` (role read from `profiles`, never from the request) to the handler. `/api/auth/logout` is the exception: it only uses `getAccessToken` (bearer or session cookie) without `withAuth`, so a blocked user can still revoke their session, and it clears both session cookies. The session is two HttpOnly cookies set by `setSessionCookies` in `api/_lib/auth.ts`: the access token (`Path=/`) and the refresh token (`Path=/api/auth`, `__Secure-` prefix because `__Host-` needs `Path=/`). `POST /api/auth/refresh` exchanges the refresh cookie for a new session and rotates both cookies (any failure or a blocked user clears them and the frontend goes to `/login`); login, refresh and `/me` return `expires_at` in the body and the frontend's `useSessionRefresh` renews shortly before it, only while the user is active (idle users lapse to `/login`); create Supabase clients only through `api/_lib/supabase.ts` (`createAnonClient()`, or `createUserClient(accessToken)` to act as the caller). Relative imports in `api/` use the `.js` extension (ESM, `"type": "module"`).

- **Sentry**: disabled when `SENTRY_DSN` / `VITE_SENTRY_DSN` is empty (unit tests, CI). Test hooks: `/?sentry-test=1` (frontend, throws asynchronously) and `/api/sentry-test` (404 in production).
